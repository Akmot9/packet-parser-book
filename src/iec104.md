# IEC 60870-5-104

IEC 60870-5-104 is the telecontrol protocol of the European electric sector, the counterpart of [DNP3](./dnp3.md): the messages of IEC 60870-5-101 over TCP 2404, the IANA port `iec-104`. It was added in 11.6.0 ([#158](https://github.com/Akmot9/Packet-parser/pull/158)), in the epic [#102](https://github.com/Akmot9/Packet-parser/issues/102) with [BACnet/IP](./bacnet.md) and [GOOSE](./goose.md). The module is `packet_parser::parse::application::protocols::iec104`, the errors are in `packet_parser::errors::application::iec104`, and the label is `"IEC 104"`.

A TCP segment carries one or more **APDUs**. Each one starts with its APCI, `0x68`, a length and a four-byte control field whose format is I, S or U; an I-format APDU then carries an **ASDU**: a type, a cause of transmission, a common address and its information objects. The crate reads them without state, and an APDU that the segment cuts short is decoded on what is left of it.

## Detection: port 2404, or Decode As

Unlike DNP3, IEC 104 is not probed blind. The APCI has no CRC, and what is fixed in it, `0x68` and a length, is two bytes: too little to probe every TCP segment with. The rule is **port-guarded**, `port_rule("IEC 104", Guard::Tcp, is_iec104_tcp_port, ProbeId::Iec104)`, 2404 on either side, rule 29 of the [table](./application.md#reading-the-table), among the port rules after RDP and before PostgreSQL. As for [every port rule](./application.md#how-the-label-is-chosen-one-ordered-table), the port is not enough: `Iec104Packet::try_from` must accept the payload, read whole rather than cut at `PROBE_CAP`. A station on another port is declared with `ParseConfig::decode_as(port, DecodeAsProtocol::Iec104)`, the variant added in 11.6.0, which is tried [before the table](./application.md#decode-as) with the same probe and the same TCP guard. Off those ports nothing recognizes IEC 104, and `Application::try_from`, the portless cascade, does not try it.

## The APCI

![The APDU of frame 9 of wireshark_iec104.pcap, 32 bits per row: the APCI with its start byte 0x68, length 14 and four control bytes announcing an I-format frame with send and receive sequence numbers 0, then the ASDU: type 100 (C_IC_NA_1), SQ 0 with one object, cause of transmission 6 (activation), originator 0, common address 10, the information object address 0 and the qualifier of interrogation 20; Iec104Packet keeps one Apdu with its format and its decoded Asdu.](images/application/iec104_struct.svg)

```rust
pub struct Iec104Packet<'a> {
    pub apdus: Vec<Apdu<'a>>,
    pub truncated: bool,       // the last APDU announces more than the segment holds
}

pub struct Apdu<'a> {
    pub length: u8,            // control field and ASDU, not the first two bytes
    pub control: [u8; 4],
    pub format: ApciFormat,
    pub asdu: Option<Asdu<'a>>,  // None for S and U, and for an I APDU cut
                                 // before the end of its ASDU header
}

pub enum ApciFormat {
    Information { send_sequence: u16, receive_sequence: u16 },  // numbered, carries an ASDU
    Supervisory { receive_sequence: u16 },                      // acknowledgement only
    Unnumbered(UnnumberedFunction),                             // link control
}
```

Like every public type of the module, they are `#[non_exhaustive]`.

| Bytes | Field | Note |
| --- | --- | --- |
| 0 | start | `0x68`, otherwise `InvalidStartByte` |
| 1 | `length` | the control field and the ASDU: 4 to 253, otherwise `InvalidLength` |
| 2–5 | `control` | read according to the format, which the two low bits of byte 2 give |

| Format | Byte 2, low bits | What the crate reads | `ApciFormat` |
| --- | --- | --- | --- |
| I | `x0` | N(S) in bytes 2–3 and N(R) in bytes 4–5, each shifted left by one bit | `Information { send_sequence, receive_sequence }` |
| S | `01` | N(R) in bytes 4–5 | `Supervisory { receive_sequence }` |
| U | `11` | the function bits of byte 2 | `Unnumbered(function)` |

The sequence numbers are read little-endian and shifted back, 15 bits each. The first control byte of a U-format APDU must carry exactly one of the six functions, otherwise it is `InvalidUnnumberedFunction`: STARTDT act `0x04` and con `0x08`, STOPDT act `0x10` and con `0x20`, TESTFR act `0x40` and con `0x80`, the variants `StartDtAct` to `TestFrCon` of `UnnumberedFunction`, whose `bits()` gives the value back. An S or U APDU is its control field alone: a length other than 4 is `ControlOnlyFormat { format, length }`, with `format` `"S"` or `"U"`.

`Iec104Packet::try_from` reads the APDUs back to back until the segment is consumed: in the corpus, 448 APDUs in 373 segments, 40 of which carry more than one, up to twelve in frame 16 of `wireshark_iec104.pcap`. Each needs its six bytes of APCI, or the decode fails with `Truncated { expected: 6, actual }`, an empty payload included.

## The ASDU

```rust
pub struct Asdu<'a> {
    pub type_id: u8,
    pub kind: Option<AsduType>,   // the type, named by its IEC 60870-5-101 mnemonic
    pub sequence: bool,           // SQ: one address, then contiguous elements
    pub count: u8,                // objects or elements announced
    pub cause: u8,                // cause of transmission, six bits
    pub negative: bool,           // P/N
    pub test: bool,               // T
    pub originator: u8,
    pub common_address: u16,
    pub objects: Vec<InformationObject<'a>>,
    pub undecoded: &'a [u8],      // what follows the objects read
}

pub struct InformationObject<'a> {
    pub address: u32,             // three bytes; in sequence, the first plus the rank
    pub element: &'a [u8],
}
```

The header is the one of IEC 60870-5-101 with the parameters of -104: a cause of transmission on two bytes, a common address on two, an information object address on three.

| Bytes of the ASDU | Field | Note |
| --- | --- | --- |
| 0 | `type_id` | named by `kind` |
| 1 | `sequence` (bit 7), `count` (bits 0–6) | a count of zero is `EmptyAsdu(type_id)` |
| 2 | `cause` (bits 0–5), `negative` (bit 6), `test` (bit 7) | for instance 6 an activation, 7 its confirmation, 20 an answer to the interrogation, which tshark names `Act`, `ActCon` and `Inrogen` |
| 3 | `originator` | originator address |
| 4–5 | `common_address` | little-endian |
| 6… | information objects | |

A complete I-format APDU whose ASDU is shorter than these six bytes is `AsduTooShort`. `AsduType` names 67 type identifications, codes 1 to 21, 30 to 40, 45 to 51, 58 to 64, 70, 100 to 107, 110 to 113 and 120 to 127, after their mnemonic: `MSpNa1` for M_SP_NA_1, `CIcNa1` for C_IC_NA_1, the first letter M for information in monitoring direction, C for a command, P for a parameter, F for file transfer. `AsduType::from_code` maps a code to its variant, and an unknown code leaves `kind` at `None`.

Each object is an address on three bytes, little-endian, and an element whose size the type fixes, from a table of IEC 60870-5-101 §7.3 internal to the crate: one byte for a single or double point, five for a short floating-point measurement, and the time tag counts, 3 bytes for a CP24Time2a and 7 for a CP56Time2a: M_SP_TB_1 is 8 bytes. With SQ = 0 every object carries its address; with **SQ = 1** only the first address is on the wire, followed by `count` elements, and the crate numbers the objects `address + rank`. `element` borrows the segment, raw: quality descriptor, value and time tag together.

The objects are read while they fit, and the rest of the ASDU is `undecoded`: nothing when everything was read, all of it when the crate has no element size for the type: an unknown type and, among the named ones, type 125, the file segment, and type 127. The decoder does not require the objects to fill the APDU exactly; in the corpus, every one of the 301 ASDUs has exactly `count` objects and nothing undecoded.

## An APDU cut by the segment

The crate is stateless and does not reassemble TCP. When the last APDU of a segment announces more bytes than the segment holds, it is decoded on what is left and `truncated` is set: its APCI is read, its ASDU too if the ASDU header is complete, with the objects that fit; if the header is not, `asdu` is `None`, which is not an error. Six bytes of APCI remain the minimum. The next segment, which starts in the middle of the APDU, is another matter: the decoder expects `0x68` at its first byte and does not look further for one, so that segment is not IEC 104. ## Validations

All of them are `Iec104ParseError`:

| Error | When |
| --- | --- |
| `Truncated { expected, actual }` | fewer than the 6 bytes of an APCI left, an empty payload included |
| `InvalidStartByte(u8)` | an APDU that does not start with `0x68` |
| `InvalidLength(u8)` | a length outside 4..=253 |
| `ControlOnlyFormat { format, length }` | an S or U APDU whose length is not 4 |
| `InvalidUnnumberedFunction(u8)` | a U-format control byte that is not exactly one of the six functions |
| `AsduTooShort(usize)` | a complete I-format APDU with less than the 6 bytes of an ASDU header |
| `EmptyAsdu(u8)` | an ASDU that announces no object |

A refused segment is not labelled, even on port 2404: it goes on to the rest of the table and usually comes out `"Unknown"`, with nothing in `corrupted`.

## Oracle: 373 segments against tshark

The golden test `tests/iec104_golden.rs` runs the five captures of `pcaps_exemple/protocols/iec104/` and compares every TCP segment that has a payload with tshark 4.6.6 without TCP reassembly (`tools/iec104_oracle.sh`, frozen in `tests/data/iec104_tshark_oracle.tsv`), APDU by APDU: length, format, U function, N(S) and N(R), and for each ASDU the type, SQ, count, cause, originator and common addresses and the address of every object. The 374 segments are all on port 2404, and all are labelled `"IEC 104"`; 373 are compared, and the other one is a retransmission, which tshark does not dissect and the crate, without a notion of retransmission, decodes like the others. That makes 448 APDUs, 301 ASDUs of 27 types, 668 information objects, 46 ASDUs in sequence and no cut APDU. A second test takes frame 9 of `wireshark_iec104.pcap` off port 2404 and back through Decode As, and refuses three single-byte alterations of it: the start byte, a length below 4, a count of zero. The fuzz target `parse_iec104` runs nightly on the same parser: the APDUs must tile the input, the last one possibly cut, every element must borrow the input, and the objects of an ASDU in sequence must be numbered one after the other.

## What is left out

- **Element values** are raw: no measured value, quality descriptor or time tag is interpreted, and causes of transmission are numbers.
- **No link state**: no tracking of the sequence numbers, of the acknowledgement windows or of the timers; one segment at a time.
- **No reassembly** of TCP, and no resynchronization inside a segment that starts in the middle of an APDU.
- **The field sizes are the -104 parameters**, fixed: a two-byte cause, a two-byte common address, a three-byte object address.
- **File transfer** segments (type 125) and type 127 stay in `undecoded`.
